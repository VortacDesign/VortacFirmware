Configuration

Config layout, the include_with template system, adding a tool, per-tool overrides, and the gantry/probing workflow.

Files under vortac_configs/ are bind-mounted into ~/printer_data/config/vortac_configs/ by install.sh and reload after git pull + systemctl restart klipper.

The include_with template system

All tools with the same PCB share one hardware template (e.g. mcu/SB2209.cfg, written against the generic MCU name EBBCan). [include_with <namespace> <file>] instantiates it once per tool:

  • Pin rewrite — every EBBCan: pin reference becomes <namespace>: (e.g. miniGrey:).
  • Section prefixing — every named section gets the namespace as a prefix: [neopixel logo_rgb] → [neopixel miniGrey_logo_rgb]. The namespace doubles as the display name in Mainsail/Fluidd/KlipperScreen, and LEDs become addressable per tool: SET_LED LED=miniGrey_logo_rgb ….
  • Singleton renaming for tool_index ≥ 1 — [extruder] → [extruder1], [fan] → [fan_generic miniGrey_fan]. Tool 0 keeps the primary extruder and the M106 fan. Reference sections (tmcXXXX, verify_heater) follow their target's rename, and whole-string section refs in values (heater: extruder → heater: extruder1) are fixed up too.
  • [vortac_tool TN] injection — the template's [vortac_tool TN] placeholder (it carries the sense pins) becomes [vortac_tool <namespace>], and tool_index, mcu_name, canbus_uuid (from the static [mcu] section) and extruder_name (the renamed extruder: extruder for index 0, extruderN otherwise) are auto-injected. Only home_dock is set per tool, via overrides:.

Good to know: what cannot be namespaced

Bare Klipper singletons without a name part (input_shaper, firmware_retraction, resonance_tester, shaketune, …) cannot be renamed. For tool_index ≥ 1 the known offenders are skipped automatically; anything else that collides across tools goes into skip_sections:. Multi-extruder naming is hardwired to extruder<N> by Klipper regardless of namespace — [extruder miniPink] is not a valid Klipper section.

Good to know: why [mcu <name>] must be static

Klipper registers MCU pin chips before extras like include_with run. So the [mcu <name>] section cannot be injected by the template — each tool file declares it statically, and the template's [mcu EBBCan] is excluded via skip_sections:. Pins must name their chip (miniGrey:PB7) — that is plain Klipper syntax.

Adding a tool — the checklist

Three conventions link everything:

  • The tool's NAME is defined exactly once — the [mcu <name>] section / include_with namespace (e.g. miniGrey). It doubles as the display name dashboards show (miniGrey_logo_rgb, …).
  • The tool's NUMBER comes from the include ORDER in tools.cfg — the first (uncommented) tool include is T0, the next T1, and so on. The first tool always owns Klipper's primary [extruder] and [fan] (hardwired by Klipper for M104/M106), so commenting a broken tool out simply renumbers the rest — Klipper never sees [extruder1] without [extruder].
  • The tool's DOCK is physical and never renumbers — set home_dock explicitly per tool via the overrides: block (vortac_tool TN.home_dock: dockX). Saved dock positions are keyed by tool name, so they survive renumbering too — and a commented-out tool's calibration survives in printer.cfg's autosave block as a harmless ghost [vortac_tool <name>] section (loaded as available: False) until the tool returns.

New-tool checklist

A missed rename does NOT error

Klipper silently merges duplicate config sections (last value wins). A copied-but-not-fully-renamed tool file therefore never errors on its own — the symptom is one franken-tool, e.g. one board shut down by the other tool's sensor config. vortac_manager catches the detectable leftovers (duplicate index/MCU/UUID/pins), but grep the file for the old name anyway — it must only appear in the two headers [mcu <name>] and [include_with <name> …].

Tool names, numbers and what stays index-based

The namespace is the display name dashboards show — name the tool after the physical tool (miniPink, miniGrey, …) and dashboards show miniPink_logo_rgb, miniPink_hotend_fan, etc. Nothing else needs to be set: tool_index comes from the include order in tools.cfg, and mcu_name/canbus_uuid/extruder_name are auto-injected into the tool's [vortac_tool <name>] section.

Only extruder/extruder1 stay index-based (hardwired by Klipper), and the T0/T1 commands plus dock0/dock1 names are index-based too (slicers emit T<n>; docks map to LED chain indices). Manager commands accept either form: VORTAC_LOAD TOOL=miniGrey and VORTAC_LOAD TOOL=T1 both work (TOOL= takes the tool name, case-insensitive, T<n>, or a bare index). Macros can address per-tool hardware uniformly via the tool's mcu_name, e.g. in tool_activate_gcode: SET_LED LED={tool.mcu_name}_logo_rgb ….

Legacy: static hand-written [vortac_tool T0] sections

A hand-written [vortac_tool T0] section still works when the PCB template carries no [vortac_tool TN] placeholder — its trailing number derives tool_index=0, mcu_name=tool0, home_dock=dock0, and the sense pins (dock_sense_pin/grab_sense_pin) go into that section directly. A trailing-numbered namespace (tool1 → 1) likewise derives the include's tool_index for non-tool templates; an explicit tool_index: option always wins.

Per-tool hardware deviations (overrides:)

Never edit the shared PCB template for one tool. Deviations go on that tool's [include_with] section, one section.key: value per line:

[include_with miniPink vortac_configs/mcu/EBB42_V12.cfg]
skip_sections:
  mcu EBBCan
overrides:
  vortac_tool TN.home_dock: dock0
  extruder.sensor_type: MAX31865
  extruder.sensor_pin: EBBCan: PA4
  extruder.spi_bus: spi1
  extruder.rtd_nominal_r: 1000
  extruder.rtd_reference_r: 4300
  extruder.rtd_num_of_wires: 2
  extruder.rtd_use_50Hz_filter: True
  • Section names are the original template names (pre-rename).
  • Pin values may be written template-relative (EBBCan: PA4) — they run through the same rewriter.
  • Keys the template lacks are added; an empty value deletes the option.
RTD pairing rule of thumb

PT100 → rtd_reference_r: 430, PT1000 → 4300 — check the reference resistor on your board. A mismatch shows up as a Thermocouple reader fault MCU shutdown (see Troubleshooting).

Homing, QGL & probing — the gantry workflow

The 4-Z gantry has two valid states, tracked by [vortac_qgl_state]: flat (top-home/frame reference — dock geometry valid) and tilted (bed reference — print geometry valid). Rules:

  • Z homing (against the top/frame) resets the state to flat and clears the stored QGL deltas — after any fresh Z home, QGL must be re-run before printing.
  • All probing requires NO tool held. The probe touch point sits above the nozzle tip whenever a tool is grabbed, so the nozzle would hit the bed before the probe triggers. The manager enforces this at the probe object itself: QUAD_GANTRY_LEVEL, BED_MESH_CALIBRATE, PROBE, PROBE_ACCURACY, … all refuse while a tool is held. Park the tool first: VORTAC_UNLOAD.
  • Tool changes handle FLAT/TILT automatically: the manager flattens the gantry for the dock motion and re-tilts afterwards — no re-probing needed.

Typical print start (no tool held yet):

G28                  # top-home -> flat
QUAD_GANTRY_LEVEL    # no tool! -> tilted
BED_MESH_CALIBRATE   # still no tool
T0                   # manager: FLAT -> fetch -> TILT, applies offsets
# print

If Z was re-homed mid-session while a tool is held: VORTAC_UNLOAD, then QUAD_GANTRY_LEVEL, then pick the tool back up.

Where the dock motion lives

  • XYZ approach/depart is hardcoded in vortac_manager.py (constants at the top of the file): DOCK_Y_SAFE = 50.0, DOCK_Z_CLEARANCE = 4.5, DOCK_APPROACH_F = 2000, DOCK_SLIDE_F = 500. Edit there for global geometry tweaks.
  • Per-tool warm-up / cool-down → tool_activate_gcode / tool_deactivate_gcode on [vortac_tool <name>] (set via include_with overrides: vortac_tool TN.tool_activate_gcode: …) — those run on either side of the dock motion.
  • Extruder switching is automatic: the manager runs ACTIVATE_EXTRUDER with the tool's injected extruder_name on every tool change — no per-tool tool_activate_gcode needed for that.
  • FLAT / TILT of the gantry around dock approach is automatic.
  • Per-tool offsets → gcode_offset_x/y/z on [vortac_tool <name>]; the manager applies them via SET_GCODE_OFFSET on every tool change.
