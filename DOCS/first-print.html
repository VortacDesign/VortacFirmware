First Print

Dry runs before filament, the print-start sequence a toolchanger needs, slicer setup, and what to watch while the first multi-tool print is running.

Before this page

The toolchanger must be calibrated (Calibration) and the printer must be levelled, meshed and offset-trimmed (Print Calibration). If a tool change is not yet reliable by hand, a print will not fix it.

1 — Dry runs, no filament

Tool changes are the one motion sequence that can wreck hardware, so exercise them cold first. With filament out and hotends off:

G28
QUAD_GANTRY_LEVEL
VORTAC_DETECT             ; establish the dock map
VORTAC_STATUS             ; sanity: tools, docks, QGL state

VORTAC_LOAD TOOL=<name>    ; pick up
VORTAC_UNLOAD             ; put back
; repeat 10× — it must be boringly identical every time

Then the same via the real command that a slicer will emit:

T0
T1
T0

Dry-run checklist

Watch the sense pins live

Run VORTAC_SENSE_MONITOR DURATION=30 in one console and trigger a tool change from another. The transitions tell you whether the grabber really hooked before the carriage moved away — much more informative than watching the toolhead.

2 — The print-start sequence

A toolchanger constrains the order, because probing is refused while a tool is held. Everything probe-based has to happen with an empty carriage, before the first Tn:

G28                       # home -> gantry flat
QUAD_GANTRY_LEVEL         # no tool held -> gantry tilted (print geometry)
BED_MESH_CALIBRATE        # or: BED_MESH_PROFILE LOAD=default
VORTAC_DETECT             # dock map — runs automatically ~3 s after startup
                          # (auto_detect, default on); keep it here as a cheap
                          # guarantee in case the auto run was interrupted
T0                        # manager: FLAT -> fetch -> TILT -> offsets -> activate
# print

A ready-made pair of macros ships as configs/vortac_configs/macros.example.cfg — see 3b — The PRINT_START / PRINT_END macros. The skeleton below is the same sequence, stripped down, so you can see what the macro is actually doing.

As a macro skeleton — adapt names and temperatures to your build; every VORTAC_* command here is real, the rest is plain Klipper:

[gcode_macro PRINT_START]
gcode:
    {% set bed = params.BED|default(60)|float %}
    {% set hotend = params.HOTEND|default(240)|float %}
    {% set tool = params.TOOL|default(0)|int %}

    M140 S{bed}                         # bed up first
    G28                                 # homing works with a tool held (sensorless Z, no probe)
    VORTAC_UNLOAD                       # make sure the carriage is empty before probing
    M190 S{bed}                         # soak while heated
    QUAD_GANTRY_LEVEL                   # leaves the gantry tilted — do NOT re-home Z after this
    BED_MESH_PROFILE LOAD=default
    VORTAC_DETECT
    T{tool}                             # pick the printing tool up
    M109 S{hotend}                      # heat the hotend that is now on the carriage
    # prime / purge line here
This skeleton heats exactly one tool

PRINT_START receives a single HOTEND value, and M109 applies it to the active extruder. Every other tool is still cold when the first T<n> happens mid-print, and the slicer's first extrusion after it dies with Extrude below minimum temp. A multi-tool print therefore needs one of the two mechanisms in Temperatures and ooze — the shipped macros.example.cfg implements both.

Two ordering traps

1. VORTAC_UNLOAD at the top only works if the machine knows it holds something. After a restart the logical state is empty even when a tool is physically grabbed — VORTAC_DETECT and the grab_sense pin are what surface that. If in doubt, look before you print.
2. Never re-home Z after QGL: that resets the gantry state to flat and clears the stored deltas, so the levelling is gone and QGL would have to run again. Home first, level second — and if you are unsure what your macro ends up in, check VORTAC_QGL_STATUS at the end of it; it must say tilted.

Good to know: what the manager does on every Tn 
tool_deactivate_gcode (old tool)
→ VORTAC_GANTRY_FLAT        (dock geometry)
→ park the old tool at its dock
→ fetch the new tool from its dock
→ VORTAC_GANTRY_TILT        (print geometry restored)
→ SET_GCODE_OFFSET          (new tool's offsets)
→ tool_activate_gcode (new tool)

No probing is involved — the FLAT/TILT replay is what makes that possible. Details in the Module Reference.

3 — OrcaSlicer setup

Vortac is a true toolchanger: one extruder per tool, each with its own hotend. In OrcaSlicer that is a multi-extruder printer profile — not "single extruder multi-material", not a filament changer.

Printer settings

Machine G-code

Machine start G-code — one line; everything else lives in the PRINT_START macro (vortac_configs/macros.example.cfg):

PRINT_START BED=[bed_temperature_initial_layer_single] TOOL={initial_extruder} HOTEND={nozzle_temperature_initial_layer[initial_extruder]} TEMPS={nozzle_temperature_initial_layer[0]},{nozzle_temperature_initial_layer[1]}

Note the indexed placeholders. nozzle_temperature_initial_layer is a vector — one entry per extruder — so it has to be indexed explicitly, otherwise a two-material print can hand PRINT_START the wrong tool's temperature. TEMPS carries the first-layer temperature of every extruder, in extruder order; add an entry when you add a tool. That is what lets the macro preheat the tools it is not starting with. Verify after slicing: the first line of the G-code must read PRINT_START BED=110 TOOL=1 HOTEND=270 TEMPS=270,265 — plain numbers, no commas inside HOTEND.

Machine end G-code:

PRINT_END

Change filament G-code — leave it empty. This is Orca's tool-change hook (PrusaSlicer calls the same field "Tool change G-code"), and empty is the correct setting here, not an oversight: with nothing in it the slicer emits the bare T<n> itself, and that single command already is the whole sequence — vortac_manager turns it into park, fetch, gantry state and offsets.

Check it in a sliced file: at the tool change you will find a lone T0 between the ramming block and the wipe tower, with no custom lines around it. That is what it should look like.

If you do put something in that field

Then it has to contain the tool command itself — the slicer only adds its own T<n> when your block does not already carry one. A block with extra commands but no T<n> gives you a print with no tool changes at all. There is no reason to fill it for a Vortac; every per-tool action belongs in tool_activate_gcode/tool_deactivate_gcode, which run inside the change where the machine state is actually known (see the park / pick hooks).

Before layer change G-code (optional, gives Mainsail a live progress estimate):

;BEFORE_LAYER_CHANGE
;[layer_z]
SET_PRINT_STATS_INFO CURRENT_LAYER={layer_num + 1}

and in Machine start G-code, after PRINT_START: SET_PRINT_STATS_INFO TOTAL_LAYER={total_layer_count}.

Exactly one PRINT_START — a second one wrecks the offsets

A duplicate line in the machine start G-code (the old one left in place above the new one) is easy to end up with and used to end in the bed. The second PRINT_START zeroes the gcode offset while the tool fetched by the first one is still on the carriage. The manager reads the live offset at the start of every tool change and treats whatever exceeds the held tool's configured offset as deliberate babystepping to carry across the change — so a zeroed offset reads as "the user babystepped by minus the whole tool offset". It carries that faithfully through the park and the next pickup, where it cancels the real offset out. The nozzle then sits one full tool offset too low.

Fixed on both sides: PRINT_START now zeroes the offset only after _VORTAC_ENSURE_EMPTY, and it aborts with a clear message if it is called twice for one print. Still: check the sliced file, PRINT_START must appear exactly once.

Do not let the slicer move the toolhead to a dock

Dock approach geometry (Y → X → Z, checked stepwise hook/unhook, dock power switching) is owned by vortac_manager. Any park/pickup move added in the slicer runs outside that logic and will crash into the dock.

Temperatures and ooze

This is where a working single-tool setup breaks the moment it becomes a multi-tool one, so it is worth being precise about who heats what.

Nothing heats the tools you are not starting with — unless you make it

Orca only emits M104/M109 for the other extruders when Emit temperature commands automatically (Printer Settings → Machine G-code) is on. With it off — and it is off in many Klipper toolchanger profiles — the entire G-code file contains no temperature command at all, and the only heating in the whole print is the M109 inside PRINT_START, which reaches the starting tool only. The first tool change then lands on a cold nozzle: "extruder" not hot enough / Extrude below minimum temp.

Check it yourself: slice, open the .gcode, search for M104.

Two independent mechanisms close that hole. Use both — they cover different failure modes.

Leave the auto-emission OFF and pass TEMPS= instead

Turning it on would also work as a bare fix for the cold nozzle, but it fights the standby temperature below: Orca re-sends the full print temperature for every extruder at the start of the second layer, overriding the drop of the tool that is parked at that moment. It also puts both hotends at full temperature before PRINT_START even runs, so they drip into the docks throughout homing, levelling and meshing.

The trade-off of leaving it off: nothing switches from the first-layer temperature to the normal one either, so the print runs at whatever TEMPS= carried. Set both to the same value in the filament profile — that is the usual case anyway.

  • TEMPS= in the start G-code (see above). PRINT_START hands one print temperature per tool to the manager with VORTAC_SET_TOOL_TEMP, keeps every nozzle at soak_temp while it homes, levels and meshes, and runs VORTAC_PREHEAT afterwards to put the idle tools on standby. This is what makes the first change fast instead of a cold start.
  • The manager's own pickup step (see Retract, standby temperature and the wait). It always waits for the arriving tool to reach temperature before anything is extruded, so a cold nozzle is structurally impossible regardless of what the slicer emitted — and there is nothing to configure or forget. If no temperature is known at all it aborts with that reason instead of a cryptic extrusion error.

Standby temperature

A parked tool keeps its board powered — an occupied dock is never de-energized — so it holds whatever target it had. At ABS temperatures that means it drips into its dock for the whole print. The manager drops the nozzle by standby_delta kelvin the moment the tool is parked and brings it back — with a wait — on pickup.

The price is heat-up time on every change: the manager cannot preheat the next tool, because when it parks one it does not yet know which one is coming. 40–60 K is the useful range — enough to stop the dripping, quick enough to come back. standby_delta: 0 turns the drop off and leaves the temperature wait in place.

Orca's own Ooze prevention does the same thing from the slicer side. Do not run both — pick one, and the firmware side is the one that also protects manual T<n> commands.

Temperature changes during the print

TEMPS= is a starting point, not a lock. The hooks track changes rather than overwriting them:

  • Changed while the tool is printing (temperature tower, per-object temperature, a slider pull in Mainsail — all of which hit the active extruder): the manager reads the live target when the tool is parked and memorises that. The new value is what comes back on the next pickup.
  • Changed while the tool is parked: on pickup the manager works out the standby value it would have left behind. If the live target is something else, that is a deliberate change — it wins, it is kept, and the console says so.
  • Below print_temp_min never counts as deliberate. That is PRINT_START holding the nozzles at soak_temp while it homes, levels and meshes; coming back up from it is exactly what the pickup step is for. Keep soak_temp at or below print_temp_min.
Temperature towers

A tower is a single-tool calibration print, so the standby mechanism never comes into play — nothing gets parked. If Orca does not emit the tower's M104 with auto-emission switched off, just switch it back on for that one print; without a second tool there is nothing for it to collide with. Either way the check is the same: search the sliced file for M104.

Retraction around the change

The slicer retracts before it emits T<n>. Everything after that — the travel to the dock row, the stepwise hook-in, the fetch of the next tool — runs on the manager's clock, and that is where the long ooze happens. park_retract in _VORTAC_PRINT_VARS adds a retraction on top for exactly that window and gives it back (plus extra_prime) on pickup. Set retract_length_toolchange per extruder in Orca as well.

Prime tower

Keep it on. With two hotends the tower is what absorbs the ooze of the tool that was idle. Place it clear of the dock approach lane — the approach moves Y, then X, then Z.

Start small

Two tools, a tall two-colour cube, one change per layer. That tells you more about repeatability than a complex model — and every change happens where you can watch it.

3b — The PRINT_START / PRINT_END macros

configs/vortac_configs/macros.example.cfg ships a ready pair. Copy it, drop the .example, and include it after tools.cfg:

[include vortac_configs/tools.cfg]
[include vortac_configs/macros.cfg]

What it does, and why in that order:

  • G28, but only when the axes are not homed yet. Homing with a tool on the carriage is fine — Z homes sensorless against the top of the frame, the probe is not involved — so a print can be started straight from a grabbed tool.
  • _VORTAC_ENSURE_EMPTY — parks whatever is held before anything probes (it homes first if PRINT_START has not, because parking is an absolute move to the dock). Probing itself stays refused while a tool is held.
  • Bed to temperature, nozzle only to soak_temp — hot enough not to sit cold, cold enough not to ooze during homing and levelling.
  • QUAD_GANTRY_LEVEL → BED_MESH_*, both with an empty carriage. No G28 Z after QGL — that would reset the gantry to flat and throw the levelling away.
  • VORTAC_DETECT only if the dock map is not valid yet (auto_detect already ran it at startup), then T<n>, then M109, then the prime line. Print temperature is only reached once the tool is actually on the carriage.
  • Both conditionals can be forced with variable_always_home / variable_always_detect in _VORTAC_PRINT_VARS.
  • PRINT_END retracts, hops, kills the hotends, runs VORTAC_UNLOAD and parks the empty carriage. CANCEL_PRINT is wrapped to go through it too — otherwise a cancelled print leaves a tool on the carriage and the next PRINT_START cannot probe.

Everything tunable (soak, standby delta, tool-change retract, prime line, park position) sits in [gcode_macro _VORTAC_PRINT_VARS]. Edit the variables, not the macros.

Retract, standby temperature and the wait

Nothing to configure. This is not a macro you have to wire up — it is vortac_manager's own behaviour, because it is identical on every machine and a print depends on it. On every tool change:

StepWhenState at that momentWhat happens
parkfirst, before any motion old tool still the active extruder, its offsets still applied, mesh still active, toolhead still at the print position extra retract (only if the nozzle can actually extrude), memorise the print temperature, drop to standby
pickuplast, after the fetch new tool active (ACTIVATE_EXTRUDER done), offsets applied, gantry tilted back, mesh restored restore the print temperature, wait for it, give the retract back plus pickup_prime_extra

Tuned with plain config options on [vortac_manager] — all with working defaults, so an untouched config already does the right thing:

[vortac_manager]
standby_delta:      50.0    # K below print temp while parked, 0 = off
standby_min:       150.0
print_temp_min:    150.0    # at/below this = machine idling, never memorised
park_retract:        1.5    # mm, 0 = off
park_retract_speed: 2400    # mm/min
pickup_prime_extra:  0.4
prime_speed:         300

VORTAC_STATUS shows the state:

Tool temps   : miniGrey=270C, miniPink=265C  [-50K, floor 150C]
Change hooks : deactivate=NONE  activate=NONE

The optional gcode hooks

tool_activate_gcode / tool_deactivate_gcode on [vortac_manager] are extension points for what is specific to your build — a purge bucket, a nozzle wipe, an LED. Both default to empty, and the retract and temperature handling run regardless, so leaving them empty is a complete setup.

Ordering is chosen so a hook always meets a hot, primed nozzle: the deactivate hook runs before the module's retract, the activate hook after the module has restored temperature and primed. The template is handed the tool the change is about ({tool.extruder_name}, {tool.tool_index}, {tool.display_name}), so one text covers every tool; a [vortac_tool] section may override either hook for one tool.

Why the retract cannot live in the slicer

The slicer retracts before it emits T<n>. Everything after that — the travel to the dock row, the stepwise hook-in, the fetch of the next tool — runs on the manager's clock, and that is where the long ooze happens. Only park_retract covers that window, and only the deactivate step reaches the old hotend at all.

Check the PAUSE park position

Mainsail/Fluidd park in a corner on PAUSE, and that corner may be a dock. The bundled [gcode_macro _CLIENT_VARIABLE] block sets a safe spot — adjust the coordinates to your machine.

4 — What to watch during the first print

  • The first change under load — stand next to it, hand on the stop. The tool is heavy and hot now; a dock position that was fine cold can bind.
  • First layer of each tool — if tool 2's first layer differs from tool 1's, that is gcode_offset_z, not a flow problem. Trim live with SET_GCODE_OFFSET Z_ADJUST=… and fold the value into the config afterwards (live adjustments are RAM only).
  • Registration between tools — colour boundaries or a two-tool alignment pattern reveal XY offset error. Fix in gcode_offset_x/y.
  • Ooze and stringing at changes — retraction and purge, not a toolchanger problem, but it looks like one.
  • Repeatability over height — errors that grow with Z point at the gantry state (was QGL actually re-run?) rather than at offsets.

5 — When something goes wrong mid-print

A tool change failed / the tool is not where the machine thinks

Stop the print. Then re-establish reality before moving anything:

VORTAC_STATUS             ; what does the manager believe?
VORTAC_SENSE_STATUS       ; what do the pins say?
VORTAC_DETECT             ; re-map docks (needs tools in docks)

If the logical state is stale but nothing is physically held: VORTAC_SET_CURRENT_TOOL CLEAR=1. If a tool is held but the manager does not know it, tell it: VORTAC_SET_CURRENT_TOOL TOOL=<name> (no motion). Only then move the carriage.

Probing suddenly refuses ("probing refused — tool … is held")

That is the probe guard, and it is usually right. Park the tool with VORTAC_UNLOAD, then probe. If no tool is physically on the carriage, check VORTAC_SENSE_STATUS — a stuck or mis-wired grab_sense pin reads as grabbed — and clear a stale logical tool with VORTAC_SET_CURRENT_TOOL CLEAR=1.

Z was re-homed while a tool was held

The gantry state is now flat and the QGL deltas are gone, so print geometry is invalid. Recovery: VORTAC_UNLOAD → QUAD_GANTRY_LEVEL → pick the tool back up. Verify with VORTAC_QGL_STATUS.

First layer is fine with one tool and wrong with another

That is per-tool Z offset, by definition — the bed mesh and the probe are tool-independent (the probe rides on the carriage). Go to per-tool Z offsets.

After every SAVE_CONFIG

It restarts Klipper, which drops the gantry tilt and the dock map. Re-run G28 → QUAD_GANTRY_LEVEL → VORTAC_DETECT before the next print — which is exactly why they belong in the print-start macro.
