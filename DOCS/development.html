Development

How changes get from your editor onto the printer, conventions to follow, and hard-won Klipper learnings.

Deployment model — no build, no tests

There is no build step, no test suite, and no linter configured. The code runs inside Klipper on a Raspberry Pi. The edit → run cycle is:

# on your machine
edit .py / .cfg  →  commit  →  push

# on the Pi
git pull            # systemd .path watcher re-runs install.sh automatically
sudo systemctl restart klipper

Because the plugins are symlinked and the configs are bind-mounted, pulling is all it takes — Klipper just needs a restart to re-import the modules.

Ad-hoc iteration without committing

dev_scripts/push_custom_scripts.py is a quick sshpass+scp pusher targeting a hardcoded Pi (192.168.0.188, user pi) — useful during tight iteration loops when you don't want to commit/pull for every attempt. Adjust the target inside the script for your network.

Conventions

  • Bilingual comments — the codebase freely mixes German and English comments (Zugriff auf ToolHead, Nun die Move-Command). Don't "translate" existing comments. Repo documentation (READMEs, these docs) is English.
  • Persisted tunables go through configfile.set(self.name, key, value) and require the user to run SAVE_CONFIG. Never write to disk directly.
  • Grabber motion: force_move.manual_move(stepper, distance, speed) followed by toolhead.wait_moves() and a small dwell to let the sensor settle. Don't drive the grabber through the kinematics path.
  • Angle math is on a circle — always wrap to [0, 360) and handle seam crossings. The wrap360 / wrap180 / circ_mean helpers in vortac_grabber.py are the reference implementations.
  • Never edit the shared PCB template for one tool — per-tool deviations go into overrides: (see Configuration).
  • Primary branch is development, not main (also install.sh's default watch branch).

Klipper learnings

Bulk angle stream is radians × 10 000

Angle bulk-sensor data from Klipper's add_client(cb) stream is in radians × 10 000. To get degrees: (raw / 10000.0) * (180 / π). This is easy to miss and produced silently wrong calibrations — which is also why VORTAC_CALIBRATE now uses direct SPI reads instead of the bulk stream (the stream was additionally lossy at sub-bit precision).

Klipper merges duplicate config sections silently

Two sections with the same name don't error — the last value wins. This is why a half-renamed tool file produces a "franken-tool" instead of a startup error, and why vortac_manager validates tool identities at connect time.

MCU pin chips register before extras run

Anything that owns pins ([mcu …]) must exist as a static config section — an extra like include_with runs too late to inject it. That's the root cause of the "static [mcu <name>] + skipped template [mcu EBBCan]" pattern.

Extra lifecycle: config parse → klippy:ready → klippy:connect

Register gcode commands at config parse; defer lookups of other objects to klippy:connect (the manager discovers tools/grabber/qgl there); hook into existing objects' internals at klippy:ready (qgl_state wraps adjust_steppers there). See the full lifecycle diagram.

Maintaining this documentation

The docs live in DOCS/ as static HTML — no build step, open DOCS/index.html in a browser (or serve the folder with python3 -m http.server).

  • Shared pieces: styling in assets/style.css, behavior (sidebar, TOC, checklists, filter, prev/next) in assets/docs.js.
  • Adding a chapter: create the page (copy an existing one as skeleton) and add one entry to the PAGES array at the top of assets/docs.js — every page's sidebar and prev/next navigation updates automatically.
  • Anchors & TOC: give every <h2>/<h3> an id; the sidebar TOC and the hover "#" links are generated from them.
  • Building blocks: callouts (.callout, variants .warn / .tip / .danger), collapsibles (details.fold), persistent checklists (.checklist with data-ck checkboxes), filterable tables (.filterbox with data-target).
  • Keep it in sync: when modules, configs, commands or workflows change, update the matching chapter in the same commit. The READMEs and this documentation should never contradict each other.
