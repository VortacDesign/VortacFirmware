KlipperScreen

Installing the touchscreen UI and adding a custom menu to it.

Status

The custom vortac_docks panel is implemented: klipperscreen/panels/vortac_docks.py in this repo, symlinked into ~/KlipperScreen/panels/ by install.sh (skipped automatically on a Pi without KlipperScreen). The repo's KlipperScreen.conf carries the matching [menu __main vortac] entry. main_menu.conf remains a reference copy of KlipperScreen's stock menu — do not deploy it.

1 — Installing KlipperScreen

KlipperScreen is a separate project that talks to Moonraker, so it is installed and updated independently of this repo. On the Pi:

cd ~
git clone https://github.com/KlipperScreen/KlipperScreen.git
./KlipperScreen/scripts/KlipperScreen-install.sh

Let Moonraker manage updates by adding this to moonraker.conf:

[update_manager KlipperScreen]
type: git_repo
path: ~/KlipperScreen
origin: https://github.com/KlipperScreen/KlipperScreen.git
env: ~/.KlipperScreen-env/bin/python
requirements: scripts/KlipperScreen-requirements.txt
install_script: scripts/KlipperScreen-install.sh
managed_services: KlipperScreen

Useful operational commands:

CommandPurpose
sudo systemctl restart KlipperScreenreload after any config change — KlipperScreen does not hot-reload
sudo systemctl status KlipperScreenis it running?
journalctl -u KlipperScreen -flive log — first stop for a blank screen or a menu that won't appear
~/printer_data/logs/KlipperScreen.logKlipperScreen's own log, incl. config and Jinja parse errors
Where the config lives

KlipperScreen reads ~/printer_data/config/KlipperScreen.conf. That is the only file you edit. Everything else — panels, the default menu, translations — lives inside the KlipperScreen installation and is overwritten on update.

Display, rotation and touch quirks

Screen size, rotation and touch behaviour are display-driver territory, not Vortac territory — follow the KlipperScreen documentation for your panel. Two [main] settings worth knowing: screen_blanking (idle blanking) and show_cursor (helpful over VNC during bring-up). The autosaved move_speed_xy/move_speed_z in this repo's KlipperScreen.conf come from the on-screen Settings panel — that is how KlipperScreen writes UI settings back.

2 — Deploying this repo's KlipperScreen config

Because install.sh does not touch these files, pick one of two approaches:

# A) copy once, edit on the Pi
cp ~/vortac/configs/klipper_screen_configs/KlipperScreen.conf ~/printer_data/config/

# B) keep it tracked in git and symlink (edits stay in the repo)
ln -sf ~/vortac/configs/klipper_screen_configs/KlipperScreen.conf \
       ~/printer_data/config/KlipperScreen.conf

sudo systemctl restart KlipperScreen

The panel itself needs no manual deployment: re-run sudo ./install.sh (or just git pull — the watcher re-runs it) and it symlinks every klipperscreen/panels/*.py into ~/KlipperScreen/panels/. Then restart both services:

sudo systemctl restart klipper          # picks up the vortac_manager status export
sudo systemctl restart KlipperScreen    # loads the panel + menu entry

The repo's KlipperScreen.conf already contains the menu entry that opens it:

[menu __main vortac]
name: Vortac
icon: extrude
panel: vortac_docks
enable: {{ 'vortac_manager' in printer.config_sections }}

Getting back to the normal menu: panels opened from a menu get KlipperScreen's standard title bar with the back arrow — one tap returns to the main menu, nothing custom needed.

Do not deploy main_menu.conf

It is a reference copy of KlipperScreen's stock menu. Copying it into ~/printer_data/config/ does nothing useful, and editing the original inside the KlipperScreen installation is overwritten on the next update. Custom menus belong in KlipperScreen.conf.

3 — Adding a custom menu

Menu items are config sections in KlipperScreen.conf whose name path defines the tree:

[menu __main vortac]                 <- entry in the main menu
[menu __main vortac grabber]         <- submenu inside it
[menu __main vortac grabber engage]  <- item inside that submenu

KlipperScreen loads its default menu first and your config on top: a new name path adds an entry, an existing one (see main_menu.conf for the stock paths) overrides the stock item.

OptionMeaning
namebutton label
iconicon name from KlipperScreen's image set (see main_menu.conf for known-good names: move, refresh, settings, extrude, bed-level, console, complete, fine-tune, info, …); an unknown name renders without an icon
panelopens a built-in panel (move, bed_mesh, gcode_macros, console, …)
method + paramscalls a Moonraker method — for G-code: printer.gcode.script with params: {"script":"…"}
confirmconfirmation dialog before running — use for anything that moves the machine or writes config
enableJinja condition; e.g. {{ 'vortac_manager' in printer.config_sections }} hides the entry on a printer without the extras

A minimal working example — one Vortac submenu with two buttons:

[menu __main vortac]
name: Vortac
icon: extrude
enable: {{ 'vortac_manager' in printer.config_sections }}

[menu __main vortac unload]
name: Park Tool
icon: home
method: printer.gcode.script
params: {"script":"VORTAC_UNLOAD"}
confirm: Park the held tool at its dock?

[menu __main vortac detect]
name: Detect Tools
icon: refresh
method: printer.gcode.script
params: {"script":"VORTAC_DETECT"}

Restart KlipperScreen and the entry appears in the main menu.

Two limits of menu buttons

Buttons cannot take parameters. Commands like VORTAC_SELECT_DOCK DOCK=… need either a fixed value baked into the button's script, or a thin gcode_macro wrapper per case (which also shows up in the stock Macros panel with zero menu config).
Buttons cannot display state. Most VORTAC_* commands answer with console text — put a panel: console shortcut next to any status button so the reply is readable. A live dock/tool display needs a custom panel, not a menu (see below).

Menu changes don't show up?
  • KlipperScreen does not reload config on its own: sudo systemctl restart KlipperScreen.
  • Edited the wrong file? Only ~/printer_data/config/KlipperScreen.conf counts — not main_menu.conf, not anything inside ~/KlipperScreen/.
  • A section that is present but invisible is usually an enable: condition evaluating false — e.g. the extras are not loaded.
  • "Section headers have extra information after brackets" — KlipperScreen's validator also scans comment lines for […] patterns. A comment like # see [menu __main vortac] breaks the whole config; write section names in comments without brackets.
  • Parse and Jinja errors land in ~/printer_data/logs/KlipperScreen.log.
Toolchanger gotchas on the stock panels
  • Bed Mesh / Z Calibrate fail with "probing refused" — that is the manager's probe guard doing its job while a tool is held. Park the tool first, then probe.
  • The temperature panel shows extruder, extruder1, … — Klipper's multi-extruder naming is hardwired; namespaced hardware (fans, LEDs) shows the display name. See pretty names.
  • The Input Shaper button is missing — its enable: guard checks for the [input_shaper] singleton, which the tool configs skip_sections:. Declare it in printer.cfg if you want the panel; background in Print Calibration → input shaper.

4 — Panel design proposal (preview)

This is a to-scale HTML mockup of the vortac_docks panel — implemented as a GTK panel with this layout in klipperscreen/panels/vortac_docks.py. It is drawn for a landscape 800×480 touchscreen (the KlipperScreen default) and deliberately always dark, like the screen itself. Every element maps to data that get_status already exports.

VORTAC Holding: miniGrey (T1) Gantry: TILTED Detection: stale — run Detect
dock0 miniPink T0 · extruder dockgrab tap → pick up (confirm)
dock1 miniGrey T1 · extruder1 dockgrab tap → park here (confirm)
dock2 — empty —   dockgrab calibrated, no tool
dock3 not calibrated   dockgrab tap → select for calibration
Park Tool
Detect
Engage
Disengage
Console

Behaviour

  • Header: held tool (current_tool, or "Carriage empty"), gantry state (qgl_state — green when TILTED, amber when FLAT during printing hours), and a detection-freshness chip (dock_detection_valid) that turns amber after a restart until VORTAC_DETECT ran.
  • One tile per dock (grid grows with dock_count). Tile state from dock_occupancy + per-tool dock_sense_state/ grab_sense_state: blue occupied, orange the held tool's origin dock, dashed = calibrated but empty, amber = no calibrated position yet. The two small dots mirror the raw sense pins — the live wiring truth, invaluable when a tile disagrees with reality. While a tool is carried, its return dock is marked "on carriage" (from the manager's park_dock status export).
  • Tap logic is contextual: occupied tile → confirm → T<n>; the held tool's tile → confirm → VORTAC_UNLOAD; uncalibrated tile → confirm → VORTAC_SELECT_DOCK DOCK=… (calibration flow). One screen, no submenu digging.
  • Action bar: a contextual primary button ("Park <tool>" while holding, "Load <tool>" when the carriage is empty and exactly one docked tool exists, otherwise it defers to the dock tiles) plus Detect, Engage, Disengage and Save Dock. Confirm policy: Detect runs immediately (harmless — LEDs are restored); everything that moves the machine or writes config confirms first. Disengage keeps its confirm deliberately: disengaging mid-air drops the tool.
  • Calibration and grabber details stay in the menu (LUT sweep, set zero, QGL flat/tilt) — the panel is for daily operation, the menu for commissioning.
Why this exact layout

The panel answers the three questions you actually walk to the printer with — what is on the carriage, what is in which dock, is the state trustworthy — without touching anything. Every action is one tap plus one confirm, with the confirm carrying the concrete consequence ("Run a tool change to T0?"). Diagnostic truth (sense dots) sits directly on the thing it describes instead of in a separate status page.

5 — Outlook: a real Vortac UI

Not built yet — recorded here so the options and their cost are on the table:

  • Level 1 — G-code macro wrappers (hours): VORTAC_UI_* macros for the parameterised commands. Visible in Mainsail, Fluidd and KlipperScreen's stock Macros panel — one implementation, every UI.
  • Level 2 — static KlipperScreen menu (hours): a button tree over those macros using the mechanics above. Config only, no code.
  • Level 3 — custom KlipperScreen panel: ✅ shipped (design preview above, code in klipperscreen/panels/vortac_docks.py). It polls vortac_manager / vortac_tool / vortac_qgl_state status once per second via printer.objects.query — deliberately independent of KlipperScreen's internal subscription machinery, to minimise breakage across KlipperScreen updates. Residual risk: the GTK panel base-class API is not versioned; a KlipperScreen update may require small adaptations (only this panel fails, the rest of the UI keeps working — check KlipperScreen.log).

Mainsail has no plugin/panel system, so a KlipperScreen menu or panel cannot be carried over — the macro layer (level 1) is the only part all UIs share.
